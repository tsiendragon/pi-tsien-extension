## 3. 为什么上下文不被约束

`~/.pi/agent/settings.json`：

```json
"compaction": { "enabled": true, "reserveTokens": 22000 }
```

主力模型窗口是 1,000,000（deepseek-v4.1-flash 等），压缩触发线 = 1M − 22K ≈ **978K**，
等于「不会压缩」。实测 `tokensBefore` 530K+ 的压缩记录证实：上下文是**涨到 20–50 万才结束**，
而不是被主动控制。压缩本身极便宜（28 次 $3.2），远低于少压缩一次省下的重放成本。

## 4. 方法与实测依据（按杠杆排序）

### L1 上下文封顶（中等杠杆，见 §7.7 的交互）
模拟口径：每次调用省 `cost_prompt × (1 − min(prompt, X)/prompt)`。

| 封顶 X | 3 天节省 | 占当前花费 |
|---|---|---|
| 80K | −$59.7 | **−59.9%** |
| 100K | −$53.5 | −53.7% |
| 120K | −$48.2 | −48.3% |
| 150K | −$41.6 | −41.7% |
| 200K | −$32.7 | −32.8% |

落地：`reserveTokens = contextWindow − X`，按模型分开设（窗口不同）：

```json
"compaction": {
  "reserveTokens": 880000,
  "keepRecentTokens": 20000,
  "modelOverrides": {
    "dashscope/deepseek-v4.1-flash": { "reserveTokens": 28000 }
  }
}
```

风险：压缩更频繁 → 早期细节被摘要化。设计文档 §7 已有「能力下限 gate」，本项必须走该 gate。

### L2 bash 结果纳入归档（覆盖 48.9% 区间）
`observation-pack` 机制为「前 2 次请求全量 → 之后 1KB 占位符 + `obs_recall` 取回」。
把 `thresholdBytes` 从 10240 降到 ~2048，即可覆盖 0.5–2K token 区间（其中 bash 106M）。
已有 S2 小样本 A/B 证据：每请求 prompt −75%~−78%、整轮 −46%~−53%、成本 −17%~−42%，
能力 gate 6/6 vs 5/6（唯一失败与机制无关）。
注意：该机制**不处理图片**（`isPureTextResult` 只接受纯文本），所以不影响 L5。

### L3 模型选择（3 天数据暴露的新问题）
| 模型 | 花费 | 占比 | 调用数 | 单次成本 |
|---|---|---|---|---|
| `dashscope/deepseek-v4.1-flash` | $55.1 | 55% | 4,089 | $0.013 |
| `dashscope/kimi-k3` | **$44.6** | **45%** | **381** | **$0.117（8.7x）** |
| `dsw/deepseek_v41_flash`（本地 vLLM） | $0 | 0% | 1,919 | — |
| `dsw/dsw/deepseek_v41_flash` | $0 | 0% | 617 | — |

- **kimi-k3 用 5% 的调用吃掉 45% 的花费**（$0.40/M prompt、$15/M output，是 deepseek 的 8x/12x）。
  审查这 381 次调用是否都必要，或降级到 deepseek-v4.1-flash，是除 L1 外最大的省钱点。
- `dsw/*`（本地 vLLM）**缓存命中率 0%**：3 天 318M token 全量 prefill。不花钱，但吃本地 GPU
  吞吐。这不是账单问题，是容量问题。

### L4 避免 session 中途切模型
36 个 session 中 **10 个在窗口内切换过模型**（如 `deepseek-v4.1-flash` ↔ `kimi-k3` /
`deepseek_v41_flash`）。每次切换都会击穿 prompt cache，后续请求按未命中价计费。
dashscope 单模型内命中率 92–97%，说明缓存机制正常，损失来自切换。
→ 长 session 尽量一个模型跑到底；需要切就 `/clear` 换新会话。

### L5 图片（不是 token 问题）
3 天 1.17 GB base64 / 1,879 张，仅占 token ~2%。若要降 token，动它收益极小；
若要降会话体积/加载时间，才考虑 `images.autoResize` 从 2000 降到 1280。

### L6 output 侧
output 占 10%（$9.5），reasoning 3.46M token。降 `defaultThinkingLevel` 有一定收益，但要按任务看。

### L7 不做
重复结果去重（0.2%）、重复 read 去重：收益远低于 L1–L3，不值得投入。

## 5. 建议执行顺序

> 注：本节顺序已被 §7 的 bash 摘要实验更新（bash 摘要是单点最大杠杆，且会大幅削弱 L1 的必要性）。

1. **bash 摘要/压缩（§7）**：实测总上下文 −51%、估计成本 −51%，摘要自身成本可忽略。
   先做确定性预处理，再只对 >300 token 的 bash 结果做 LLM 摘要，原文归档可召回。
2. **L4 避免中途切模型**：零成本，直接生效（3 天 10/36 个 session 切过）。
3. **L3 审查 kimi-k3 调用**：381 次调用占 45% 花费，逐类判断能否降级。
4. **重新测量后再决定 L1**：bash 上下文若先降 51%，平均 prompt 会从 198K 降到约 100K，
   那时 270K 的 compaction 封顶基本不再触发。不要两个大机制同时上（§7.7）。
5. L2 / L6 顺手改。

一次只验一个机制。验证用 `extensions/trajectory-recorder.ts` 计时账本 + `extensions/usage-analytics.ts`，
对比「平均 prompt token / 每次调用成本 / 压缩次数 / 任务通过率」。

## 6. 追问答复（compact 触发点 / compact 优化 / bash 摘要）

### 6.1 主动 compact 是否有问题？能在 270K 触发吗？

**更正本文件早前口径**：触发点不是 978K。仓库内 `extensions/auto-compact-1m.ts`（已在
`extensions.config.json` 的 loadOrder 中）对窗口 ≥1M 的模型在 **50%** 处提前 `ctx.compact()`：

```
1,048,576 × 0.5 = 524,288
```

3 天 28 次压缩的 `tokensBefore` 常见 530K，正好印证 524K 是实际触发点。

| 封顶 X | 3 天节省 |
|---|---|
| 524K（现状） | −2.7% |
| 400K | −10.1% |
| 350K | −15.0% |
| 300K | −20.9% |
| **270K** | **−24.9%** |
| 200K | −36.2% |
| 150K | −46.1% |

结论：现状 524K 的触发点基本等于「放任增长」，只省下 2.7%；压到 270K 就能拿回约 25%。

**改法**：`DEFAULT_TARGET_PERCENT = 0.5` → `0.26`（0.26 × 1,048,576 = 272K）。建议顺手改成
可配置项（配置文件或按模型），不要硬编码。

注意事项：

- 该扩展仅对 `contextWindow >= 1M` 的模型生效；3 天主力模型都命中
  （`dashscope/deepseek-v4.1-flash` 1,048,576；`dashscope/kimi-k3` 1,048,576）。
- **不要用 `compaction.reserveTokens` 调触发点**：官方文档明确 `reserveTokens` 同时决定摘要
  输出预算（`reserveTokens: 0` 会把摘要预算归零）。用扩展的 `ctx.compact()` 干净得多。
- 压缩后只保留 `keepRecentTokens`（默认 20K），上下文会在 **20K ⇄ 270K** 锯齿波动，
  均值约 (270+20)/2 ≈ 145K。
- 风险：压缩更频繁 → 模型重新探索被摘要掉的细节，可能增加轮数。必须走能力 gate。

### 6.2 compact 本身可以优化吗？

可以，四个方向：

1. **触发点**（6.1，−25% 起，最大单项）。
2. **摘要模型换便宜 non-thinking 模型**：`pi.on("session_before_compact")` 可自供摘要，
   官方示例 `examples/extensions/custom-compaction.ts` 就是用 gemini-flash 替代主模型。
   当前摘要用主模型跑、平均 prompt 104K token（`kimi-k3` 时既贵又慢）。但 3 天压缩总共只花
   $3.2，**省钱有限，主要收益是延迟**。
3. **`keepRecentTokens` 调小**（20K → 8K）：压缩后起点更低。风险：刚完成的工作被摘要掉。
4. **摘要内容定向**：强制摘要包含「命令 / 退出码 / 关键错误 / 文件路径与行号 / 数字 / 下一步命令」，
   减少后续重跑；不要往摘要里塞 bash 全文。这一项与 6.3 互补。

### 6.3 用 non-thinking 便宜 LLM 总结 bash 输出，可行吗？

**技术可行，且 API 现成**：

- `pi.on("tool_result", async (event, ctx) => { ... })` 可返回 `{ content, usage }` 改写结果
  （RTK 正是这样做的）；`ctx.signal` 支持 Esc 取消。
- `ctx.modelRegistry.streamSimple(model, context, { reasoning })` 可调用任意已配置模型
  （`azure-okx/gpt-5.6-luna`、`dashscope/qwen3.8-flash`），不需要自建 HTTP 客户端。
- 设计文档 §3 已把这条列为「委托层 Evidence-Preserving Reducer ❌ 缺（另案）」，属规划内。

**但实测数据不支持「每次 bash 都总结」**：

| 指标 | 3 天实测 |
|---|---|
| bash 结果数 | 5,325 |
| bash 原始 token | 1.87 M（平均 **352 token**） |
| RTK 截断命中 | 仅 16 次 |
| bash 在上下文中的累计 token | **212.6 M（占 67.6%）** |
| 放大倍数 | **≈114x** |

**关键：bash 的问题不是「输出太大」，而是「同一批小输出被重放上百次」。**
对每次 bash 加一次 LLM 调用（5,325 次 ≈ agent 自身调用量的 74%）把 352 → 200 token，
只省约 43% 的 bash token，却引入同等量级的额外往返与延迟 —— 不划算。

应该这样做：

1. **先上确定性、零延迟的手段**：降低 observation-pack 阈值（占位符 + `obs_recall` 归档），
   对**已存在的结果整体替换**，而不是对每个新结果做摘要。模拟显示「bash 结果 >500 token 压到
   200」可让总上下文 −35%（≈成本 −35%），其中大部分可由占位符以零 LLM 调用拿到。
2. **LLM 摘要只用于大输出**：3 天仅 **1,205 次 >500 token**（455 次 >1000），占 bash 上下文
   token 约 64%。只对这部分做 ≈400 次/天，摘要成本 <$1/3 天，延迟可控。
3. **摘要必须可召回**：复用 observation-pack 的归档 + `obs_recall`，摘要只作索引，原文仍可
   取回。摘要把关键错误行删掉是这类方案最大的失败模式。
4. **摘要输出结构化**：退出码 / 关键错误 / 文件与行号 / 计数 / 下一步命令，而非自由文本。
5. **并发限流 + fail-open**：bash 常并行，摘要调用要限流；失败一律返回原文。
6. **绝不用主模型做摘要**，用 luna / qwen3.8-flash（non-thinking）。

**收益不能简单相加**：触发点（6.1）与 bash 压缩（6.3）降低的是同一个量（平均 prompt 大小）。
建议先做触发点，再叠加摘要/占位符，分步实测。

## 7. bash 输出专题：形态、可压缩度与摘要实验

### 7.1 bash 输出长什么样（3 天实测，5,398 条）

| 特征 | 实测 |
|---|---|
| 原始 token | 1.89 M（平均 **352 token**） |
| RTK 截断命中 | 仅 16 次（0.3%） |
| **复合命令**（含 `&&` / `;`） | **93.7%** |
| 带 `== 标签 ==` 分节 | 42.5%（2,294 条，约 4,100 个分节） |
| 空行占比 | 11.0% |
| 纯标签行占比 | 3.5% |
| 同一输出内重复行占比 | 2.0%（**行级去重没用**） |
| 首行 ≤10 token | **66.3%** |

按命令类别（3 天 token）：

| 类别 | token | 次数 | 平均 token | 平均行数 |
|---|---|---|---|---|
| `echo`（多段拼接检查） | 494,076 | 830 | 595 | 46.9 |
| `python3` | 226,876 | 1,003 | 226 | 13.5 |
| `sed` / `cat` / `ls`（文件浏览) | 459,675 | 1,094 | 420 | 31.1 |
| `grep` | 178,386 | 508 | 351 | 21.2 |
| `git` | 76,202 | 260 | 293 | 22.4 |

**结论**：bash 输出不是「一个命令一个大结果」，而是**一次 bash 里把多次检查打包**
（`cd X && echo "== A ==" && cat f && echo "== B ==" && ls ...`），其中很多分节对下一轮推理并不需要。

### 7.2 能压到什么程度（真实实验）

实验条件：`dashscope/qwen3.8-flash`、`enable_thinking: false`、`temperature: 0`、`max_tokens: 96`、
prompt 要求「目标 40 token，保留错误/路径/行号/数字/标识符，丢弃样板与重复」，30 条分层样本（3 天真实数据）。

| 子集 | 原始 | 摘要 | 压缩比 |
|---|---|---|---|
| 全部 30 条 | 16,757 | 1,354 | **8.1%**（压缩 92%） |
| **>500 token（11 条）** | 11,987 | 665 | **5.5%** |
| ≤300 token（13 条） | 2,404 | 458 | 19.1% |

对比 `dashscope/deepseek-v4.1-flash`：9.5%，p50 延迟 1.39s（略快）。

**对照基线**：确定性规则（去 ANSI/空行 + 同输出内行去重 + 按分节各留头尾 8 行）只能压 **38.3%**。
LLM 摘要明显更强，因为它能判断「哪些行才是结论」。

### 7.3 延迟（用户的判断成立）

| 配置 | p50 | p90 | max |
|---|---|---|---|
| `max_tokens=256`（宽松） | 2.56 s | 4.59 s | 12.43 s |
| **`max_tokens=96`（目标 40 token）** | **1.60 s** | 2.17 s | 2.49 s |
| 同上（deepseek-v4.1-flash） | 1.39 s | 1.70 s | 1.94 s |

- 输出长度确实是延迟主因之一：把上限从 256 收到 96，p50 从 2.56s 降到 1.60s。
- **但有长尾**：报错类样本重测时出现 9.4s / 13.3s 的离群调用 → 必须设超时兜底。
- 对照基线：本机 bash 命令平均耗时 **26.9 s**
  （`usage-analytics.json`：64,478 次 / 1.736 亿 ms）。+1.6s ≈ **+6%**。
- 摘要自身成本：约 **$0.00005/次**；647 次/天 → **$0.10 / 3 天**，可忽略。

### 7.4 端到端收益（按 3 天 prompt 成本 $91.8 口径）

摘要比例按实测分档（≤100 token 不动；100–200 → 35%；200–300 → 25%；300–500 → 19%；
500–1000 → 8%；>1000 → 5.5%）：

| 只摘要 bash 结果 > | bash 上下文 | 总上下文 | 估计成本 | 摘要调用量 |
|---|---|---|---|---|
| 500 token | −59.9% | −41.7% | −$38.3 | 1,213 / 3d |
| **300 token** | **−73.2%** | **−51.0%** | **−$46.8（−51%）** | **1,940 / 3d（647/天）** |
| 100 token | −83.8% | −58.3% | −$53.5 | 4,797 / 3d |

### 7.5 实测发现的风险

1. **摘要当「索引」很好，当「替代品」会出事**。抽查大输出，摘要稳定保留了表名/列数/分区/
   函数名/常量/版本（例：2,500 token → 70 token，仍含 `dwd_okx_..._df: 31 cols, pt YYYYMMDD`）。
   但如果输出是**源码 dump**，摘要会压成「文件+函数名列表」，agent 之后仍要 `read` 重读 → 反而多一轮。
2. **原文必须可召回**。否则一旦摘要丢了关键行，无法恢复。复用 observation-pack 的归档 + `obs_recall`。
3. 「错误行是否保留」这类自动质量指标**不可靠**：抽查发现 12 条所谓「错误行」里多数只是含
   `error` 字样的源码行（`throw new Error`），不是真报错。质量评估必须人工抽查 + 保留原文兜底。
4. 长尾延迟（实测 9–13s）需要超时与限流。

### 7.6 建议方案（分层，先确定性后 LLM）

1. 只对 **>300 token** 的 bash 结果做摘要（占结果数约 36%，覆盖约 85% 的 bash 上下文 token）。
2. 先跑确定性预处理（剥 ANSI、去空行、按 `== 标签 ==` 分节、去重复行），再送 LLM：
   降低输入量、降低输出波动。
3. LLM 用 non-thinking 小模型（`qwen3.8-flash` / `deepseek-v4.1-flash`），`temperature=0`
   （可复现 + prompt cache 稳定），`max_tokens≈96`。
4. **原文归档 + 摘要里带 obs id**，agent 要细节时 `obs_recall`。
5. 超时（≤3s）与并发限流；失败一律返回原文（fail-open）。
6. 排除「源码 dump」类输出（启发式：命令含 `sed -n` / `cat *.py`，或输出含大量
   `def ` / `function ` / `{`）。

### 7.7 与 compaction 的关系

7.4 与 §6.1 降低的是同一个量（平均 prompt 大小），**不能简单相加**。
若 bash 上下文先降 51%，平均 prompt 会从 198K 降到约 100K，p90 从 422K 降到约 200K，
那时 270K 的 compaction 封顶基本不再触发。
→ **先做 bash 摘要，再重新测量，最后才决定是否需要改 compaction 触发点。**

## 8. 未验证与风险

- 节省预测基于「成本 ≈ 与 prompt 线性」，忽略每次调用约 $0.01 的固定开销，实际节省略低于表中数字。
- L1 的能力影响**未做实验**：压缩更频繁可能增加重读与返工轮数。必须走能力 gate。
- 3 天样本仅 36 个 session、7,006 次调用，且模型构成（kimi-k3 占 45%）与历史整体差异大，
  结论的稳定性弱于全量口径；L1 的百分比建议按全量口径（cap 120K ≈ −28%）保守估计。
- 未区分「任务本身需要」与「浪费」，只做总量归因；L1/L2 省的是「重放次数」，不是结果体积本身。
